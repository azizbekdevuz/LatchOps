# LatchOps Recovery Review 최종 보고서

**부제**: Git 병합 충돌 복구를 위한 증거 기반 AI 설명과 사람 승인 워크플로
**범위**: 사고 유형 1개(`merge_conflict`), 로컬 전용, Next.js 16 · TypeScript · Prisma
**작성일**: 2026-11-19

> 정직성 고지
> - 이 보고서의 모든 수치는 저장소의 평가 하네스(`apps/web/scripts/review/evaluate.eval.ts`)가 생성한 `docs/submission/results/` 파일에서 그대로 옮겼습니다.
> - 사용자 인터뷰, 설문, 현장 사용자 연구는 **수행하지 않았습니다**.
> - 수용 기준(80%, 10%, 0건, 100%)은 **목표치**입니다. 미달 항목은 미달로 보고합니다.
> - 중간 발표 제안서(6쪽) 원문은 저장소에 없습니다. 따라서 과제 요구사항 문서에 적힌 범위와 기준을 따랐습니다.

## 1. 요약

LatchOps는 원래 위험한 Git 상태를 결정적 규칙으로 분류하고 복구 계획을 만드는 도구였습니다(기존 `state-engine`, `recovery-engine`, CLI). 중간 발표 시점의 데모(`/hacksprint`)는 버튼을 누르면 계획을 곧바로 격리 환경에서 실행했습니다. 설명은 선택적 원격 LLM(Nosana)이 자유 형식으로 작성했습니다.

최종 제출에서는 기존 엔진을 **수정하지 않고 재사용**합니다. 그 앞에 **Recovery Review** 단계를 새로 만들었습니다.

1. **증거(Evidence)**: 기존 엔진의 스냅샷·계획을 번호 매긴 증거 항목(E1..En)으로 바꿉니다. 비밀값을 마스킹하고 재검사한 뒤 SHA-256으로 고정합니다.
2. **근거 있는 설명(Grounded explanation)**: 사용자가 그 증거 해시에 동의한 경우에만 로컬 모델(Ollama, Qwen2.5 3B)을 호출합니다. 모든 주장은 증거/런북 ID를 인용해야 합니다. **fail-closed 검증기**는 근거 없는 핵심 주장, 명령어, 성공 단정이 하나라도 있으면 설명 전체를 숨깁니다.
3. **명시적 승인(Explicit approval)**: 요청자가 아닌 승인자가 결정적 계획의 대안 하나를 사유와 함께 승인합니다. 승인은 30분 동안만 유효하고 1회만 쓸 수 있습니다.
4. **격리 실행**: 서버가 사고를 새 임시 저장소에 다시 만들고 상태 해시를 재검증합니다. 결정적 인가 함수(13개 조건)를 통과하면 승인된 계획 명령만 실행합니다. 판정은 기존 `verifyRecovery`가 내립니다.

결정적 평가 20개 시나리오에서 측정한 결과는 다음과 같습니다(§7).

- 판정 일치: 기준선 12/20(60.0%)에서 최종 **20/20(100.0%)**으로 높아졌습니다.
- 차단해야 할 시나리오에서의 실행: 기준선 7/7에서 최종 **0/7**로 줄었습니다.
- 승인 없는 실행: 기준선 20/20에서 최종 **0/20**으로 줄었습니다.
- 심어 둔 비밀값의 모델 입력 유출: 기준선 3/3에서 최종 **0/3**으로 줄었습니다.

로컬 3B 모델의 실제 설명 결과는 §7.3에 있습니다.

## 3. 문제 정의와 범위

### 3.1 문제

병합 충돌을 복구할 때 위험은 두 가지입니다.

- **잘못된 설명을 믿는 위험**: LLM이 충돌 원인이나 파일 내용을 지어내면, 검토자는 존재하지 않는 근거로 잘못된 쪽을 선택할 수 있습니다. 소형 오픈소스 모델은 한국어 환각 탐지에서도 정확도가 낮다고 보고되었습니다[R6].
- **승인 없는 실행 위험**: 계획이 맞더라도 상태가 바뀐 뒤 실행하거나, 권한 없는 사람이 실행하거나, 저장된 계획이 변조되면 사고가 커집니다.

국내 지침도 같은 방향을 요구합니다. 인공지능기본법은 고영향 AI 사업자에게 결과 설명 방안과 사람의 관리·감독, 조치 문서의 보관을 요구합니다[R1 제34조]. 관련 가이드라인은 사람이 개입할 기준과 방법을 미리 정하라고 안내합니다[R3]. 국가정보원 지침은 생성물 재검증과 민감정보 입력 금지를 권고합니다[R4]. Git 복구 도구는 법상 고영향 영역이 아니지만, 이 원칙들을 설계 기준으로 삼았습니다.

### 3.2 범위 (중간 발표 범위 유지)

- 사고 유형: `merge_conflict` 1개. 다른 유형의 스냅샷은 가져오기 단계에서 422로 거부합니다.
- 로컬 전용: Next.js 서버(127.0.0.1), 로컬 Ollama, 로컬 SQLite. 외부 API 호출이 없습니다.
- 스택: 기존 Next.js/TypeScript/Prisma를 그대로 씁니다. 기존 PostgreSQL 스키마와 별개로 Recovery Review 전용 SQLite Prisma 스키마를 추가했습니다.
- 실행 대상: 서버가 만든 **임시 재현 저장소만** 대상입니다. 사용자의 실제 저장소(CLI 가져오기)에는 아무것도 실행하지 않습니다.
- 금지: 자동 push/merge, 모델이 만든 명령의 실행.

## 4. 시스템 설계

전체 구조와 다이어그램은 `ARCHITECTURE.md`에 있습니다. 여기서는 세 단계의 설계 결정을 설명합니다.

### 4.1 증거 스냅샷 (신규 `evidence.ts`, `redact.ts`)

- **입력**: 기존 `captureSnapshot`, `computeRepoSignals`, `generateRecoveryPlan`이 만든 `SnapshotV1`, `RepoSignalsV1`, `RecoveryPlanV1`.
- **항목화**: 분류, 진행 중 작업(`MERGE_HEAD`), 병합 메시지, 브랜치, 작업 트리 개수, 충돌 블록(ours/theirs), 최근 커밋, reflog, 계획 요약, 대안을 각각 E# 항목으로 만듭니다. 모델과 검토자가 같은 ID로 같은 사실을 가리키게 하기 위해서입니다.
- **신뢰 표시**: 커밋 메시지·파일 내용·병합 메시지는 `untrusted`로 표시합니다. 간접 프롬프트 인젝션 대비입니다[R12][R13].
- **비밀값 처리**: 13종 규칙으로 마스킹합니다(개인키, AWS, GitHub, Slack, `sk-`, Google, JWT, URL 자격증명, Bearer, 비밀 키-값, 이메일, 홈 경로 등). 이어서 재검사(`verifiedClean`)를 하고, 프롬프트를 만든 직후 한 번 더 검사합니다. 하나라도 남아 있으면 모델을 호출하지 않습니다(422).
- **잘림과 커버리지**: 충돌 측당 600자, 커밋 30개 등 상한을 두고 잘린 사실을 기록합니다. 기존 캡처가 미병합 파일을 5개까지만 담는 제한이 있습니다. 그래서 원시 `git status`의 미병합 항목 수와 비교하고, 차이가 있으면 "커버리지 공백" 증거를 만들어 실행을 차단합니다(S11).
- **고정**: 정규화 JSON의 SHA-256(`evidenceHash`)과 계획 지문(`planFingerprint`, 생성 시각 제외)을 계산합니다. 동의, 설명, 승인은 모두 이 해시에 묶입니다.

### 4.2 근거 있는 설명 (신규 `prompt.ts`, `llm.ts`, `retrieval.ts`, `validate.ts`)

- **동의**: `ConsentRecord`는 (증거 해시, 제공자)에 묶입니다. 증거가 바뀌거나 동의를 철회하면 다시 동의해야 합니다. 동의 없는 호출 시도는 409로 거부하고 감사 로그에 남깁니다(S14).
- **모델**: 로컬 Ollama `qwen2.5:3b`를 temperature 0, seed 7로 호출합니다. 출력 JSON 스키마는 Ollama `format`으로 강제하고 출력 토큰은 최대 1,200개입니다. CPU에서 응답 헤더 타임아웃(300초)을 넘지 않도록 스트리밍으로 받습니다.
- **출력 계약**: `summary`, `claims[]`(id, text, type, key, citations, confidence), `uncertainties[]`(1개 이상), `recommendedAlternativeId`(계획의 대안 또는 null), `humanDecisionNeeded`.
- **검증(fail-closed)**: JSON과 스키마, 인용 ID의 실제 존재, 주장 속 경로·OID·`KEY=VALUE`·설정 키·숫자가 인용 항목에 있는지, "N개 파일" 같은 개수가 맞는지 확인합니다. 금지 내용(위험 Git 명령, 계획 밖 명령, 셸 명령, "VERIFIED/안전/승인/푸시 준비" 단정, 검토 불필요 주장, 계획에 없는 추천)도 검사합니다. 핵심 주장 중 하나라도 근거가 없으면 설명 전체를 **보류**하고 사유만 보여 줍니다.
- **스칼라 정규화**: 소형 모델은 `"null"`, `"true"`를 문자열로 출력하는 경우가 있습니다. 이 두 종류의 철자만 타입을 바꾸고, 바꾼 내역을 `normalizations`에 기록합니다. 내용 텍스트는 절대 바꾸지 않습니다. 평가에서는 정규화 없이 승인된 비율도 따로 보고합니다.
- **모델의 권한**: 설명은 판정(VERIFIED/FAILED), 승인, 실행 명령 중 어디에도 입력되지 않습니다. 모델 추천이 엔진 추천과 다르면 경고로만 표시합니다.

### 4.3 명시적 승인과 결정적 인가 (신규 `authorize.ts`, `service.ts`, `audit.ts`)

- **역할**: `viewer`(읽기), `requester`(사고 생성·동의·설명·실행 요청), `approver`(승인/거절).
- **승인 규칙**: 승인자 역할이어야 하고 요청자 본인이면 안 됩니다(4-eyes). 사유는 5자 이상이고, 대안은 결정적 계획에 있는 것만 고를 수 있습니다. 승인은 증거 해시·계획 지문에 묶이며 30분 후 만료됩니다.
- **인가 함수**: `authorizeExecution()`은 모델 출력을 입력으로 받지 않는 순수 함수입니다. 13개 조건은 `ARCHITECTURE.md` §3에 있습니다. 실행 직전 재현 저장소의 상태를 다시 캡처해 해시가 다르면 차단하고(S12), 저장된 계획을 다시 지문화해 변조되었으면 차단합니다(S16).
- **격리 실행**: OS 임시 디렉터리에 저장소를 만들고 커밋 날짜를 고정합니다. 전역 Git 설정은 차단하고(기존 `isolatedGitEnv`), 원격이 없는지 확인합니다. 해결본 파일은 "사람이 준비한 시나리오 고정 해결본"으로 표시하고, `git add` 전에 충돌 마커를 검사합니다(S04). 판정은 기존 `verifyRecovery` + `decideVerdict`, 인가 거부는 `BLOCKED`입니다.
- **감사 로그**: 모든 상태 변경(생성, 증거, 동의, 설명, 결정, 실행, 거부)을 `sha256(prevHash|incident|actor|action|payload)` 체인으로 저장합니다. 상세 화면을 열 때마다 체인을 검증하며, 변조는 E2E 테스트로 확인했습니다.

### 4.4 UI (신규 `/review`, `/review/[id]`)

- **목록 화면**: 4단계 흐름, 로컬 모델 상태, 시나리오 20개(저장소 12 + 안전 통제 8), CLI 스냅샷 가져오기, 최근 리뷰를 보여 줍니다.
- **상세 화면**: 왼쪽에 증거(해시, 마스킹 보고, 잘림 기록, 항목)를 고정해 두고, 오른쪽에 설명 → 계획 → 결정 → 실행 → 감사 순서로 패널을 둡니다. 인용 칩을 누르면 해당 증거가 강조됩니다. 보류된 설명은 내용 대신 사유만 보입니다. 실행이 끝나면 승인 폼과 실행 버튼이 사라집니다.
- 화면 캡처는 `screenshots/`에 있습니다.

## 5. RAG vs 직접 컨텍스트 주입: 왜 RAG인가

### 5.1 비교 설계

| | 직접 주입 | RAG (pinned + BM25) |
|---|---|---|
| 증거 | 전부 | 핵심 고정 항목 + BM25 상위 6 |
| 런북(K1–K12) | 전부 | BM25 상위 3 |
| 같은 점 | 같은 모델, 같은 시스템 프롬프트, 같은 출력 스키마, **같은 fail-closed 검증기** | |

순수 벡터 RAG가 아니라 "고정 + 어휘 검색"을 택한 이유는 세 가지입니다.

1. 검토에 반드시 필요한 사실(분류, `MERGE_HEAD`, 충돌 수, 계획, 대안)은 검색 점수와 무관하게 항상 들어가야 합니다. 그래서 이 항목들은 고정합니다.
2. 증거 텍스트는 경로·키·커밋 메시지처럼 **정확한 문자열**이 중요합니다. 따라서 BM25[R14]가 적합하고, 별도 임베딩 모델 없이 로컬에서 결정적으로 재현됩니다.
3. 국내 연구에서도 검색 범위를 줄이고 근거 제약을 거는 방식이 Faithfulness를 높였다는 보고가 있습니다[R7]. 반대로 검색 품질 향상이 생성 정확도로 곧바로 이어지지 않는다는 보고도 있습니다[R9]. 그래서 RAG를 가정하지 않고 **직접 주입과 같은 조건에서 측정**했습니다.

### 5.2 측정된 컨텍스트 크기 (모델 호출 없이 결정적으로 계산)

`results/EVAL_DETERMINISTIC.md`의 프롬프트 문자 수입니다.

| 시나리오 | 증거 항목 | 직접 주입 (문자) | RAG (문자) | 감소율 |
|---|---|---|---|---|
| S01 기본 | 16 | 6,034 | 3,180 | 47.3% |
| S10 긴 히스토리 | 34 | 9,132 | 4,151 | 54.5% |
| S11 파일 7개 | 21 | 7,357 | 4,286 | 41.7% |

직접 주입은 증거가 늘수록(긴 히스토리, 다수 파일) 선형으로 커집니다. RAG는 고정 항목 + 상위 k개로 상한이 있습니다. 긴 컨텍스트는 지연·비용을 늘리고, 중간에 있는 정보의 활용도도 떨어뜨릴 수 있습니다[R11].

### 5.3 정확도·지연·비용 실측

## 7. 평가

### 7.1 방법

- **시나리오 20개**(`scenarios.ts`): 각 시나리오는 임시 디렉터리에 실제 Git 저장소를 만들고 고정 날짜로 커밋한 뒤 병합 충돌을 재현합니다. 저장소 시나리오 12개(S01–S11, S20)와 안전 통제 시나리오 8개(S12–S19)로 나뉩니다. 목록은 `EVALUATION_KO.md` §2에 있습니다.

## 8. 한계

1. **소형 로컬 모델의 품질**: 3B 모델은 CPU에서 호출당 수 분이 걸리고, 근거 규칙을 자주 어깁니다. 검증기는 이런 출력을 보류하므로 안전하지만, 그만큼 "설명 없이 증거만으로 결정"하는 경우가 늘어납니다.
2. **검증기의 범위**: 엔티티(경로, 키-값, 숫자, OID)와 인용 존재는 검사합니다. 하지만 문장의 의미가 인용 항목과 논리적으로 일치하는지(함의)는 검사하지 않습니다. 엔티티가 없는 일반 문장은 인용만 있으면 통과할 수 있습니다.
3. **표본 크기**: LLM 평가는 시나리오당 모드별 1회(temperature 0)입니다. 통계적 유의성을 주장하지 않습니다.
4. **프롬프트 조정 편향**: 출력 길이·주장 수 규칙(시스템 프롬프트 7번)과 스키마 상한은 S01 개발 중 실제 출력을 보고 추가했습니다. S01은 평가 집합에도 포함되어 있습니다.
5. **기존 캡처 제한**: 미병합 파일 5개 제한은 기존 엔진의 한계입니다. Recovery Review는 이를 탐지해 차단할 뿐 해결하지 않습니다(S11).
6. **식별·인증**: 데모 사용자 토큰은 로컬 데모용입니다. 실제 인증(기존 NextAuth)과 연동하지 않았습니다. Host 헤더 검사는 위조될 수 있으므로 반드시 `pnpm review:dev`(127.0.0.1 바인딩)로 실행해야 합니다.
7. **격리 실행 대상**: 격리 실행은 서버가 재현한 시나리오 저장소에서만 가능합니다. CLI로 가져온 실제 저장소 스냅샷은 검토만 가능합니다. 실제 저장소에서 복구하려면 사람이 승인된 계획을 직접 실행해야 합니다.
8. **비용 수치**: 로컬 실행 비용은 0입니다. 호스팅 API 비용은 가정 단가($0.15/M 입력, $0.60/M 출력)로 계산한 **가상 값**이며 실제 청구 금액이 아닙니다.
9. **사용자 평가 부재**: 실제 개발자 대상 사용성·신뢰도 평가는 하지 않았습니다.

## 9. 재현 방법

```powershell
pnpm install
pnpm review:setup                                   # 엔진 빌드 + review Prisma 클라이언트
pnpm review:test                                    # 단위 + E2E (모델 불필요)

$env:REVIEW_EVAL_LLM='1'; pnpm review:eval          # + 로컬 모델 평가 (CPU에서 1.5시간 이상)
pnpm review:dev                                     # http://127.0.0.1:3000/review
```

## 10. 결론

Recovery Review는 기존 결정적 엔진을 바꾸지 않고, 그 앞에 증거 고정, 근거 검증, 사람 승인, 결정적 인가, 감사 기록을 추가했습니다. 결정적 평가에서 판정 일치와 무단 실행 0건 목표를 달성했습니다. 비밀값 유출도 기준선 3/3에서 0/3으로 줄었습니다. 로컬 소형 모델의 설명 품질은 §7.3의 측정값 그대로이며, 시스템은 품질이 낮은 설명을 사용자에게 보여 주지 않는 쪽(fail-closed)으로 설계했습니다.
